# Task 1.7 を本番で最短で解く動き方（テキストファイルからのコピペ前提・事前設定を踏まえた手順設計）

## 質問

```
CCIE_train_hub/Questions/pattern2/pattern2_q7.md この問題を最短で解くときの動きを指南して
本番ではテキストファイルにコンフィグをコピペして使いまわせる
なので必要な設定をするのにショートカットできる
事前設定を踏まえてどう動くのが最短か考えて
```

## 回答

### 結論：差分を探さず、冪等な完成形ブロックを6回貼る

事前設定を「打つ量を減らす材料」に使うのは**遅い**。6台分の `show` で差分を洗うのに3〜5分かかるが、
冪等なコマンドを余分に貼るコストはゼロ。

**事前設定の知識は、打つ量の削減ではなく「落とし穴の察知」にだけ使う。**

→ 最短は「機器別に完成済みブロックを6個用意し、順に貼る」。本番での編集・判断はゼロ。

---

### 1. 貼る順番（唯一意味のある判断）

```
R3 → R4 → R5 → R6 → R1 → R2
```

理由: R1/R2 の `mpls ldp password required for 11` は**未認証ピアを拒否する**。
PE 側に鍵が入る前に打つと LDP が落ちた状態が続き、「壊した？」と時間を溶かす。
PE 4台を先に固めれば、**R2 を打ち終えた瞬間に5セッション全部が上がる**ので、そのまま検証へ直行できる。

各ブロック内の順序も固定:
`ldp router-id + パスワード` → `OSPF` → `インタフェース`
（`force` は LDP セッション確立後に打つと張り直しになるため必ず先頭）

---

### 3. なぜブロックが2種類で固定できるか（本番でインタフェース判断をしない根拠）

`EI_v2.yaml` の links セクションで確定済み:

| 機器 | コア内リンク（設定する） | CE 向け（触らない） |
|---|---|---|
| R1 | Gi0/0↔R2、Gi0/1↔R3、Gi0/2↔R5 | — |
| R2 | Gi0/0↔R1、Gi0/1↔R4、Gi0/2↔R6 | — |
| R3〜R6 | **Gi8 のみ** | R3: Gi1↔R11, Gi2↔R21 / R5: Gi1↔R61 / R6: Gi1↔R62, Gi2↔R70 |

- R1/R2 は3本ともコア内 → `interface range Gi0/0-2` で一括して安全。
- PE は Gi8 一本だけ。Gi1/Gi2 に OSPF や `mpls ip` を入れると顧客向けにラベルが漏れる。

→ 本番では考えず、ブロックを信じて貼る。

---

### 4. 事前設定に起因する落とし穴3つ（テンプレが自動で潰す）

| 罠 | 実態 | テンプレ側の対処 |
|---|---|---|
| **R5 に OSPF が皆無** | `router ospf 1` すら無い。R1 の `sh ip ospf nei` が**2行しか出ない**原因 | R5 ブロックが丸ごと新規投入 → 自動解決 |
| **R4 の Lo0 が /31** | `100.255.254.4 255.255.255.254`（EI_v2.yaml 2770行）。LDP router-id / iBGP update-source の /32 前提と噛み合わない | R4 ブロック先頭に `/32` 修正を1行仕込み済み |
| **`FULL/DR` は「上がってる」ではなく「違反」** | broadcast のままだと DR が **Type 2 LSA を生成** = 要件違反 | 6台全部に P2P。ネットワークタイプは Hello に含まれないため**片側だけでは Type 2 が消えない** |

3つ目が本問の本体。**「事前設定でネイバーが上がっている」≠「要件を満たしている」**。

---

### 5. 検証は R1 と R2 の2台だけで足りる（約40秒）

エリア0の LSDB は全台で同一なので、**Type 2 の不在は R1 一発で6台分の証明になる**。

```
! R1 で
sh ip ospf neighbor                        → 3行、全て FULL/  -  （DR が残っていたら P2P 漏れ）
sh ip ospf database network                → 空          （Type 2 LSA なしの直接証明）
sh ip route ospf | i 100.0.                → 空          （prefix-suppression = トランジット情報なし）
sh mpls ldp neighbor | i Peer              → 3ピア        （R2/R3/R5）
sh mpls ldp neighbor detail | i Password   → required / in use

! R2 で
sh ip ospf neighbor                        → 3行、全て FULL/  -
sh mpls ldp neighbor | i Peer              → 3ピア        （R1/R4/R6）
```

LDP セッションは全部で5本（R1-R2 / R1-R3 / R1-R5 / R2-R4 / R2-R6）。
R1 で3本 + R2 で3本 → 重複1本を除いて**5本すべてを網羅**。PE 4台への個別ログインは不要。

---

### 所要時間の目安

準備済みなら **貼り6回で約2分 + 検証40秒 = 合計3分強**。
本番で頭を使うのは「順番（PE→P）」と「R4 の /31」の2点だけ。残りはすべてファイルに追い出せる。

### 補足: 手打ちせざるを得ない場合の短縮策

PE 4台のブロックを完全に同一化したい場合、全 PE に以下2行を両方入れる手がある:

```
mpls ldp neighbor 100.255.254.1 password CCIE!nfr4
mpls ldp neighbor 100.255.254.2 password CCIE!nfr4
```

存在しないピア向けの行は無害で、「ピア単位で MD5 認証」の要件は満たす。
ただし**事前にブロックを用意できるなら不要**（貼るコストは同じ）。あくまで手打ち時の保険。
