# Task 1.8 R3 だけ vrf forwarding + ip address が必要な理由と「アクティブな BGP ピア 5 つ」の正体

## 質問

```
interface GigabitEthernet1
vrf forwarding fabd2
ip address 100.3.11.1 255.255.255.252

interface GigabitEthernet2
vrf forwarding fabd2
ip address 100.3.21.1 255.255.255.252
```

CCIE_train_hub/Questions/pattern2/pattern2_q8.md で R3 だけこれらの設定が必要なのはなぜ

「R3 と R6 では、アクティブな BGP ピアが 5 つ存在する状態にすること。」と問題文にあるが、
R3 においてこのアクティブなピアとはなんの機器のことで、どんな IP で指定している？

## 回答

### 1. なぜ R3 だけ VRF + IP アドレスを打ち直すのか

理由は 2 段構えです。

#### (a) R3 は初期コンフィグが「まっさら」な唯一の PE

EI_v2.yaml の初期コンフィグを PE 4 台（R3〜R6）で比較すると差は明白です。

| | `vrf definition fabd2` | CE 向け I/F の `vrf forwarding` | `router bgp 10000` |
|---|---|---|---|
| **R3** | **なし** | **なし**（Gi1/Gi2 は global に IP） | **なし** |
| R4 | あり（rd 10000:4 / RT 10000:4） | あり（Gi1.100 等） | あり（iBGP VPNv4 まで完成） |
| R5 | あり（rd 10000:5 / RT 10000:1） | あり（Gi1） | あり（VRF 内 eBGP まで完成） |
| R6 | あり（rd 10000:6 / RT 10000:1） | あり（Gi1, Gi2.100） | あり（VRF 内 eBGP まで完成） |

R3 の初期コンフィグ（EI_v2.yaml, node id `n15`）はこうなっています。

```
interface GigabitEthernet1
 ip address 100.3.11.1 255.255.255.252   ← global routing table
!
interface GigabitEthernet2
 ip address 100.3.21.1 255.255.255.252   ← global routing table
!
interface GigabitEthernet8
 ip address 100.0.13.2 255.255.255.252
 ip ospf 1 area 0
!
router ospf 1
（router bgp も vrf definition も存在しない）
```

つまり **R3 だけは L3VPN の PE として何も出来ていない**ので、VRF 定義・RD/RT・
インターフェイスの VRF 所属・BGP プロセス全部をゼロから作る必要がある。
R4/R5/R6 の解答が「RT を 10000:1 に揃える + `neighbor ... password`」だけの
短い差分になっているのは、残りが初期コンフィグ投入済みだからです。
**「解答に書かれていない = 不要」ではなく「もう入っている」**というパターン
（Task 1.6 の R62 と同じ罠）。

#### (b) `vrf forwarding` を入れると IP アドレスが消える（IOS の仕様）

Gi1/Gi2 は初期コンフィグですでに `100.3.11.1/30` と `100.3.21.1/30` を持っています。
それでも解答に `ip address` が書いてあるのは、**アドレスを変更しているのではなく、
消えるので同じ値を再入力している**からです。

```
R3(config-if)# vrf forwarding fabd2
% Interface GigabitEthernet1 IPv4 disabled and address(es) removed due to enabling VRF fabd2
```

インターフェイスの所属 VRF を変える＝ルーティングインスタンスを移す操作なので、
IOS は古い L3 設定（IPv4 アドレス、場合により ACL・NAT 等）を安全のため破棄します。
**必ず `vrf forwarding` → `ip address` の順**で、逆順や打ち忘れをすると
インターフェイスが no ip address のまま残り、この後の eBGP が一切上がりません。
本番で最も踏みやすい落とし穴です。

#### (c) そもそも Gi1/Gi2 が VRF に入らないといけない理由

R3 の 3 本のインターフェイスは役割が違います。

| I/F | 対向 | 属すべき場所 | 理由 |
|---|---|---|---|
| Gi8 | R1（P ルータ） | **global**（VRF に入れない） | MPLS アンダーレイ。OSPF area 0 + LDP が走る SP コア側 |
| Gi1 | **R11**（HQ の CE, AS 65001） | **VRF fabd2** | PE-CE リンク＝顧客側 |
| Gi2 | **R21**（DC の CE, AS 65002） | **VRF fabd2** | PE-CE リンク＝顧客側 |

MPLS L3VPN の大原則は「**PE-CE リンクは顧客 VRF、PE-P リンクは global**」。
Gi1/Gi2 を global に置いたままだと具体的にこう壊れます。

1. `address-family ipv4 vrf fabd2` 配下の `neighbor 100.3.11.2` が **VRF fabd2 の
   ルーティングテーブルから 100.3.11.2 への経路を引けない**（global にしかない）ため、
   TCP 179 が張れず eBGP セッションが Idle のまま。
2. `redistribute connected` が拾うのは **VRF fabd2 の connected だけ**。global に
   ある 100.3.11.0/30・100.3.21.0/30 は VPNv4 に載らず、対向拠点へ広告されない。
3. 顧客経路が global に漏れる＝L3VPN の分離（アドレス重複の許容・テナント隔離）が崩壊する。

### 2. R3 の「アクティブな BGP ピア 5 つ」の正体

**iBGP（VPNv4）3 本 + eBGP（VRF fabd2）2 本 = 5** です。

| # | ピア機器 | 指定 IP | 種別 | AS | 由来の IP | アドレスファミリ |
|---|---|---|---|---|---|---|
| 1 | **R4**（PE） | `100.255.254.4` | iBGP | 10000 | R4 の **Loopback0** | `address-family vpnv4` |
| 2 | **R5**（PE） | `100.255.254.5` | iBGP | 10000 | R5 の **Loopback0** | `address-family vpnv4` |
| 3 | **R6**（PE） | `100.255.254.6` | iBGP | 10000 | R6 の **Loopback0** | `address-family vpnv4` |
| 4 | **R11**（HQ の CE） | `100.3.11.2` | eBGP | 65001 | R3 Gi1 ↔ R11 Gi0/0 の **直結 /30 の対向側** | `address-family ipv4 vrf fabd2` |
| 5 | **R21**（DC の CE） | `100.3.21.2` | eBGP | 65002 | R3 Gi2 ↔ R21 Gi1 の **直結 /30 の対向側** | `address-family ipv4 vrf fabd2` |

配線の裏付け（EI_v2.yaml `links:`）:

- 4469 行: `R11-GigabitEthernet0/0<->R3-GigabitEthernet1`
- 4476 行: `R21-GigabitEthernet1<->R3-GigabitEthernet2`
- 4658 行: `R3-GigabitEthernet8<->R1-GigabitEthernet0/1`（コア側なので BGP ピアではない）

対向側の初期コンフィグも一致します（CE 側は投入済み、R3 側だけ空）。

```
R11: router bgp 65001 / neighbor 100.3.11.1 remote-as 10000
R21: router bgp 65002 / neighbor 100.3.21.1 remote-as 10000
```

R11 は SW101/SW102/R12 とつながる **HQ サイト**、R21 は SW201/SW202/R22 とつながる
**DC サイト**の出口ルータです。

#### iBGP と eBGP で IP の指定方針が違う理由

- **iBGP（PE 間）は Loopback0 を使う**: `update-source Loopback0` とセット。
  PE 間は R1/R2 経由のマルチホップで、物理リンクが 1 本落ちても OSPF が迂回すれば
  Loopback 到達性は残る → **セッションが切れない**。VPNv4 の next-hop も Loopback に
  なり、LDP のラベルが Loopback 宛に張られているので MPLS 転送と整合する。
- **eBGP（PE-CE）は直結 /30 の対向アドレスを使う**: 直結 1 ホップなので Loopback を
  使う理由がない（使うなら `ebgp-multihop` + 相互の Loopback 経路が別途必要になる）。
  リンクが落ちればセッションも落ちるべき、という設計。

#### 「アクティブな」の二重の意味 — `no bgp default ipv4-unicast` が効いている

R3 の解答には `no bgp default ipv4-unicast` があります。これがあると
`neighbor X remote-as` を書いただけでは**どのアドレスファミリでも有効化されない**ので、
セッションが Established になりません。だから解答は必ずファミリごとに `activate` します。

```
 address-family vpnv4
  neighbor 100.255.254.4 activate     ← ここで初めて iBGP 3 本が「アクティブ」に
  neighbor 100.255.254.5 activate
  neighbor 100.255.254.6 activate
 !
 address-family ipv4 vrf fabd2
  redistribute connected
  neighbor 100.3.11.2 remote-as 65001
  neighbor 100.3.11.2 activate        ← ここで eBGP 2 本が「アクティブ」に
  neighbor 100.3.21.2 remote-as 65002
  neighbor 100.3.21.2 activate
```

`activate` を落とすと neighbor 行はあるのにピアが数に入らない、という減点の典型です。
検証は `show bgp all summary` で **5 行**（VPNv4 に 3、`vrf fabd2` に 2）が
Established（State/PfxRcd が数字）になっていることを見ます。

### 3. 対比: R6 も 5 つだが、やることは password だけ

問題文が「R3 **と R6**」と限定しているのは、この 2 台だけがピア 5 本だからです。

| PE | iBGP | eBGP（VRF 内） | 計 | Pattern 2 で必要な作業 |
|---|---|---|---|---|
| R3 | R4/R5/R6 | R11(65001), R21(65002) | **5** | **全部ゼロから** |
| R4 | R3/R5/R6 | （VRF 内 eBGP なし） | 3 | RT を 10000:1 に + password |
| R5 | R3/R4/R6 | R61 側 100.5.61.2(65006) | 4 | RT 確認 + password |
| R6 | R3/R4/R5 | R62 100.6.62.2(65006), R70 100.6.70.2(65007) | **5** | **password のみ** |

R6 は初期コンフィグの時点で VRF も VPNv4 も VRF 内 eBGP も完成しているので、
Pattern 2 の解答は `neighbor ... password CC!E!nfr4` × 3 だけ。
**「R6 も 5 本にしろ」と言われても R6 側で作るものはほぼ無い**、という点に注意。

### 4. RT を 10000:1 に揃える意味（ついでに）

R3 の VRF は `rd 10000:3` / `route-target import・export 10000:1`。
RD は PE ごとに一意（経路の識別子）でよいが、**RT は 4 台全部 10000:1 に揃える**
ことで、どの PE がエクスポートした VPN 経路も他の全 PE がインポートする
= フルメッシュ VPN になります。R4 は初期が `10000:4` なので
`no route-target both 10000:4` で消してから `10000:1` を入れ直す必要があります
（R5/R6 は CML の初期コンフィグ上すでに 10000:1）。
RT がバラバラだと BGP セッションは全部上がるのに `show ip route vrf fabd2` に
他拠点の経路が入らない、という切り分けの難しい状態になります。
