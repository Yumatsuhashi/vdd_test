# Task 1.7 `access-list` の番号が 11 である理由（数字に必然性はない／Pattern 3 は同じ役割で 10／制約は「標準 ACL であること」だけ／`option 1 for 11` の 1 は ACL 番号ではない）

## 質問

access-listの番号が11だけどこれはなぜ？

## 回答

### 結論

`mpls ldp password option 1 for 11 CC!E!nfr4` の `11` は、
**LDP パスワードを適用するピア集合を定義した標準 ACL の番号**。
1〜99 のどれでも動作は同じで、**11 でなければならない理由はない**。

技術的な制約は「標準 ACL の番号レンジ（1–99 / 1300–1999）であること」だけ。

---

### 証拠: Pattern 3 は同じ役割で `10` を使っている

`original/RS コンフィグ パターン比較` Task 1.7 の R1 欄を横に並べると:

| | Pattern 1 | Pattern 2 | Pattern 3 |
|---|---|---|---|
| ACL | （なし） | `access-list **11** permit 100.255.254.2/.3/.5` | `access-list **10** permit 100.255.254.2` |
| 用途 | LDP 認証なし | `mpls ldp password option 1 for 11` | `mpls ldp session protection for 10` |

R2 も同様（Pattern 2 = `access-list 11` に .1/.4/.6、Pattern 3 = `access-list 10` に .1）。

同じ「LDP ピアの一覧を作る ACL」なのに、パターンによって 11 だったり 10 だったりする。
**番号は作問者が用途ごとに割り振っただけ**で、技術的な意味を持たない。

---

### 技術的な制約は 3 つ

#### 1. 標準 ACL（1–99 / 1300–1999）でなければならない

`mpls ldp password option <n> for <acl>` が受け取れるのは **standard ACL**。
マッチさせたいのは **LDP ピアの LDP router-id（= 相手の Loopback0 の /32）** という
単一の送信元 IP だけなので、送信元しか見ない標準 ACL で必要十分。

11 は 1–99 の範囲なので標準 ACL。ここが唯一の「満たさなければならない条件」。
100 番台（拡張 ACL）では通らない。

```
access-list 11 permit 100.255.254.2    ← R2 の Lo0（LDP-ID）
access-list 11 permit 100.255.254.3    ← R3 の Lo0
access-list 11 permit 100.255.254.5    ← R5 の Lo0
```

**これはパケットフィルタではない。**「この 3 台を認証対象グループとする」という**名簿**として使われる。
ACL の permit/deny がトラフィックを落とすわけではない。

#### 2. `option 1` の「1」は ACL 番号ではない ← 本当の罠

```
mpls ldp password option 1 for 11 CC!E!nfr4
                        ↑        ↑
                        │        └─ ACL 番号（= 11）
                        └─ 優先順位（precedence）。ACL とは無関係
```

`option <n>` は複数の password option を並べたときの**評価順序**（小さい番号から評価）。
ここが両方とも数字なので、ACL を 1 番にすると `option 1 for 1` となって読み手が混乱する。
**11 なら 2 つの数字を目視で区別できる**という意味では合理的
（ただし作問者の意図として明記された資料はないので推測）。

#### 3. ラボ内で番号が衝突しないこと

`EI_v2.yaml` を grep したところ **初期コンフィグには access-list が 1 件も存在しない**（0 件）。
つまり「既存 ACL を避けて 11 にした」わけではない。

Pattern 2 全体で使われる番号付き ACL は 2 つだけで、衝突していない:

| 番号 | タスク | 用途 |
|---|---|---|
| **11** | Task 1.7 | LDP 認証対象ピアのグループ定義（R1/R2） |
| 66 | Task 1.9 系 | BGP `neighbor 100.5.61.2 distribute-list 66 in/out` |

名前付き ACL（`CCIENAT` / `CCIETELNET` / `ACCESS` / `snmp-service`）は別枠なので無関係。

---

### 本番で本当に気をつけるべきこと

番号が何番かは採点されない（問題文に番号の指定がない）。**危険なのは番号のズレ。**

```
access-list 11 permit 100.255.254.2
mpls ldp password option 1 for 1 CC!E!nfr4    ← 1 と 11 を打ち間違えた
mpls ldp password required for 11
```

こう打っても **IOS はエラーを出さない**。存在しない ACL 1 を参照した状態になり、
「誰にもマッチしない = パスワードが一切適用されない」まま素通りする。
しかも `required for 11` 側は生きているので、**LDP セッションが上がらなくなって初めて気づく**という最悪の順序になる。

打った後は必ずこの 3 つで突き合わせる:

```
show access-lists 11              ← R1/R2 とも 3 行出るか。空なら番号ズレ
show mpls ldp parameters          ← password option / required が 11 を参照しているか
show mpls ldp neighbor detail     ← 実際に MD5 が効いているか
```

`show access-lists 11` は Pattern 2 の検証コマンド表にも
「R1/R2: LDP neighbor ACL 確認」として明記されている（Pattern 3 は `show access-lists 10`）。

---

### 一般化できる教訓

ラボ解答に出てくる**番号（ACL 番号・route-map の seq・isakmp policy 番号など）は、
問題文で指定がない限り任意**。暗記すべきは数字ではなく「参照している側と一致させる」構造。

- `access-list **11**` ←→ `password option 1 for **11**` ←→ `password required for **11**`
- 3 箇所すべてが同じ番号を指していること **だけ**が要件

同種の論点: `crypto isakmp policy` の番号が 10 である理由（Task 1.11 の QA）も同じ構図。
