# Task 1.3 root guard をこのポート範囲にかける理由（Gi0/3 の正体＝モジュール0で唯一残ったL2ポート）

## 質問

SW101において

```
interface range GigabitEthernet1/0-3, GigabitEthernet2/0-1, GigabitEthernet0/3
spanning-tree guard root
```

このインターフェースにだけ対して spanning-tree guard root しているのはなぜ？　gi0/3 が特に意味がわからない　物理トポロジではどこにも繋がっていないしね
SW102 に対しても同様に回答して

## 回答

### 結論

範囲の選定基準は「**L3化されずに L2 のまま残っている＝STP が動きうるポート全部**」。
Gi0/3 が入っているのは、**Gi0 モジュールで唯一 `no switchport` されていない生き残りの L2 ポート**だから。

Gi0/3 がどこにも繋がっていないという指摘は正しい（`EI_v2.yaml` の links に SW101-Gi0/3 / SW102-Gi0/3 のエントリは存在しない。`topology1.png` で SW101 の下に見える「G0/3」は R11 側のポート名ラベル）。

### SW101 のポート棚卸し（全12ポート）

CML 上の SW101（iosvl2）は Gi0/0-0/3, Gi1/0-1/3, Gi2/0-2/3 の12ポート構成。

| ポート | 初期状態 | 接続先 | STP | root guard |
|---|---|---|---|---|
| Gi0/0 | `no switchport`（L3） | R11 Gi0/3 | 対象外 | なし（設定不可） |
| Gi0/1 | `no switchport`（L3） | R12 Gi0/2 | 対象外 | なし |
| Gi0/2 | `no switchport`（L3） | SW201 Gi1/2（DC） | 対象外 | なし |
| **Gi0/3** | **既定の L2 のまま** | **未接続** | **動く** | **あり** ← 質問の対象 |
| Gi1/0 | 既定の L2 | 未接続 | 動く | あり |
| Gi1/1 | 既定の L2 | 未接続 | 動く | あり |
| Gi1/2 | L2 trunk | SW110 Gi1/0（Po1） | 動く | あり |
| Gi1/3 | L2 trunk | SW110 Gi1/1（Po1） | 動く | あり |
| Gi2/0 | L2 trunk | SW102 Gi2/0（Po3） | 動く | あり |
| Gi2/1 | L2 trunk | SW102 Gi2/1（Po3） | 動く | あり |
| Gi2/2 | 既定の L2 | 未接続 | 動く | なし（後述の漏れ） |
| Gi2/3 | 既定の L2 | 未接続 | 動く | なし（後述の漏れ） |

**Gi0/0-0/2 が範囲から抜けているのは「繋がっていないから」ではなく「L3 ルーテッドポートだから」**。ルーテッドポートでは STP が動かず BPDU も受け取らない。Gi0 モジュール4本のうち3本が L3 化されていて Gi0/3 だけが L2 のまま取り残されている ——「Gi0/3」という一見唐突な指定はこの消去法の結果。

### なぜ未接続ポートにまでかけるのか

**1. 要件がポート単位ではなくスイッチ単位で書かれている**

> SW101およびSW102は、本社内の他のスイッチから受信する、より優先度の高いBPDUの影響を受けないようにしてください。

「このポートで」ではなく「このスイッチが」影響を受けるな、という書き方。BPDU が入ってきうる経路（＝STP が動く全ポート）を塞ぐのが素直な解釈。

**2. root guard は副作用がゼロ**

root guard は **superior BPDU を受信したときだけ**発動する。何も繋がっていないポート、PC しか繋がらないポートでは一生発動しない。かけ得なので迷ったら広めにかけるのが定石。

**3. 未使用ポートこそ本来の防御対象**

Gi0/3・Gi1/0-1 は空きポート＝将来誰かが勝手にスイッチを挿しうる場所。しかもこの解答は `spanning-tree portfast edge default` を入れているので空きポートは全部 edge ポート扱いになる。「エッジのつもりのポートにスイッチが挿された」瞬間に遮断する、という組み合わせが成立する。

### なぜ BPDU guard ではなく root guard なのか

要件の後半がそのまま root guard の動作仕様。

> より優先度の高いBPDUを受信している**間は**、その受信ポートでトラフィックを転送してはいけません。

- **root guard**: superior BPDU を受けている間だけ `root-inconsistent`（ブロック）→ 受信が止まれば**自動復旧**。「受信している間は」に一致
- **BPDU guard**: BPDU を1つ受けただけで err-disable → 手動復旧か errdisable recovery が必要。「受信している間は」という条件付き挙動にならない

### SW102 の場合

範囲は `GigabitEthernet1/0-3, GigabitEthernet0/3` ＋ `port-channel 2`。**Gi2/0-1 と Po3 が意図的に外れている**。

| ポート | 接続先 | root guard |
|---|---|---|
| Gi0/0 | R12 Gi0/3（L3） | なし（STP対象外） |
| Gi0/1 | R11 Gi0/2（L3） | なし（STP対象外） |
| Gi0/2 | SW202 Gi1/2（L3、DC） | なし（STP対象外） |
| **Gi0/3** | **未接続** | **あり**（SW101 と同じ理屈） |
| Gi1/0-1 | 未接続 | あり |
| Gi1/2-3 | SW110 Gi1/2-3（Po2） | あり |
| **Gi2/0-1** | **SW101 Gi2/0-1（Po3）** | **意図的に除外** |
| Gi2/2-3 | 未接続 | なし（漏れ） |
| Po2 | → SW110 | あり |
| **Po3** | **→ SW101** | **意図的に除外** |

除外の理由は、SW101（priority 0）からの BPDU は SW102（priority 4096）にとって**正当に superior** だから。ここに root guard をかけると Po3 が `root-inconsistent` でブロックされ、SW102 は SW101 をルートと認識できなくなり自分がルートになってしまう。要件「SW101 をルート、SW102 をセカンダリルート」を自分で壊すことになる。

要件文の「**本社内の他のスイッチ**から受信する、より優先度の高いBPDU」において、SW102 にとって SW101 は「より優先度の高い BPDU を送ってよい唯一の正当な相手」であり、警戒対象の「他のスイッチ」ではない、という読み分け。

### 補足1: Gi2/2-3 は範囲から漏れている

厳密に「STP が動く全ポート」を網羅するなら Gi2/2-3 も対象のはずだが、解答の範囲に入っていない（原本 HTML の比較表で Pattern 1/2/3 すべて `row-common` = 同一）。実害はない（実際に他スイッチと繋がる Gi1/2-3・Gi2/0-1・Po1・Po3 は押さえてあるので要件は満たす）が、**「全 L2 ポートに機械的にかけた結果」ではなく「図に出てくるポート＋モジュール単位でざっくり拾った結果」**である点は認識しておく。自分で解くときは `Gi0/3, Gi1/0-3, Gi2/0-3` の方が要件文に忠実。

なお原本の差分サマリーには「1.3 … guard rootのポート番号 (g0/3 vs g0/2)」という記述があるが、実際の config 比較表では Pattern 1/2/3 で範囲が完全一致しており、このサマリー行は実態と合っていない。

### 補足2: 物理ポートと Po の両方にかけている理由

一般に EtherChannel メンバーの STP 設定は Po 側が支配する。物理側にもかけているのはバンドルが解けて単独ポートに戻ったときの保険。

### 確認コマンド

```
show spanning-tree inconsistentports          ← root-inconsistent で止まっているポート
show spanning-tree interface Gi0/3 detail     ← "Root guard is enabled" の表示
show running-config | include guard           ← 適用漏れの洗い出し
show spanning-tree vlan 2000                  ← SW101がルート／SW102のPo3がルートポートか
```
