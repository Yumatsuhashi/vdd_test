# Pattern 2 全体 — `CCIE!nfr4`(`CC!E!nfr4`)が使われるタスク一覧と、事前の鍵設定が必要なものの整理

## 質問

CC!E!nfr4というパスワードが何回も登場しますが事前の鍵の設定が必要なものとそうでないものがあると思います
各タスクで何にCC!E!Nfr4を使っていてそれは事前設定が必要なのか整理してください

## 回答

Pattern 2 の `Questions/pattern2/*.md` 全体を検索した結果、このパスワードは **7つのタスク（q5, q6, q7, q8, q10, q11, q12, q14）** で使われている。
用途別に整理すると、事前設定の要不要は次の3パターンに分かれる。

### パターンA: 完全新規（候補者が両端に一から設定する。事前設定なし）

| Task | 用途 | 対象デバイス |
|---|---|---|
| q5 (1.5) | OSPF MD5認証（`ip ospf message-digest-key 1 md5`） | SW101/SW102/R11/R12 |
| q6 (1.6) | EIGRP Named Mode MD5認証（key chain `CCIE_MD5`） | R61（R62は`key-string`定義以外はプリステージ済み） |
| q7 (1.7) | LDP MD5認証（グローバル/ピア単位） | R1〜R6（Global SP #1） |
| q8 (1.8) | BGP(VPNv4/iBGP) neighbor password | R3〜R6 |
| q10 (1.10) | BGP(eBGP) neighbor password（R5–R61間のみ。R6–R62間はパスワード要求なし） | R5, R61 |
| q12 (1.12) | ローカルユーザー`username ccieuser password`（Telnetログイン用） | R23単体（相手側R24は打つだけなので鍵交換ではない） |

これらは `EI_v2.yaml`（CMLラボの初期コンフィグ）を grep しても該当行が一切なく、**候補者がゼロから両端（または単体）に値を入力する**タスク。
値そのものは事前に決まっているわけではなく、要件文に書かれた値をそのまま使うだけでよい。

補足: q10 の問題文自体は「MD5フラグを付与すること」としか書いておらず、パスワードの値を明示していない。公式解答は Task 1.8 で
既に使っている同じ値を暗黙に再利用しているだけで、ラボ全体でMD5/PSK系の値は基本的にこの1つに統一されている。

### パターンB: 事前設定済みのプレースホルダーキーを置き換える（部分的に事前設定あり）

| Task | 用途 | 対象デバイス |
|---|---|---|
| q11 (1.11) | DMVPN/IPsec の事前共有鍵（ISAKMP PSK） | R24（ハブ）, R61/R70（スポーク） |

`EI_v2.yaml` には Task 1.11 対象デバイスの初期コンフィグとして、すでに **ダミーの鍵 `cisco`** が入っている。

- R24: `crypto isakmp key cisco address 0.0.0.0`（1709行）
- R61: `crypto isakmp key cisco address 0.0.0.0`（3193行）
- R70: `crypto keyring KR vrf WAN` + `pre-shared-key address 0.0.0.0 0.0.0.0 key cisco`（3537-3538行）

つまり「鍵をやり取りする仕組み（ISAKMP policy / keyring）自体はすでに存在」しており、候補者がやるのは
**値をデフォルトの`cisco`から`CC!E!nfr4`へ置き換える**こと（`no crypto isakmp key cisco ...` → `crypto isakmp key CC!E!nfr4 ...`）。
q5/q6/q7/q8/q10/q12 のような「箱ごと新規作成」とは異なる。

### パターンC: 相手側（バックエンド）に本物の鍵がすでに実在し、それに合わせる（最も強い意味での「事前設定が必要」）

| Task | 用途 | 対象デバイス |
|---|---|---|
| q14 (1.14) | RADIUS共有鍵（NAS-サーバ間） | SW211（ISE役はFreeRADIUSコンテナ） |

問題文は「ISEサーバには次の設定が行われています」という前提で `RADIUSキー: CCIE!nfr4` を提示している。このラボでは実機ISEの代わりに
`EI_v2.yaml` に組み込まれた **FreeRADIUSコンテナ**が動いており、その初期コンフィグ（プリステージ済み・候補者は一切触らない）に
RADIUS共有鍵と認証ユーザーが**すでに実在**している。

```
# clients.conf（NASクライアント許可リスト）
client ccie      { secret = CC!E!nfr4 }   # 4304行
client 10.2.252.1 { secret = CC!E!nfr4 }  # 4311行

# users（RADIUSユーザーDB）
iseuser Cleartext-Password := "CC!E!nfr4"  # 4344行
```

したがって q14 だけは、候補者が新しい値を決めて両端に入れるのではなく、**すでにバックエンドに存在する値と一致させるために
SW211側を後から合わせる**という、他の6タスクとは性質が異なるタスクになっている。

## 重要な注意（実機で詰まりやすい2点）

1. **綴りの不一致**: 問題文はすべて `CCIE!nfr4`（C-C-I-E-!）と表記されているが、`original/` の公式解答configおよび
   `EI_v2.yaml` の実データは一貫して **`CC!E!nfr4`**（C-C-!-E-!、"I"がなく"!"になっている）。
   q5〜q12（パターンA/B）は候補者が両端を新規設定するので綴りはどちらでも動作はするが、公式解答と一致させたいなら`CC!E!nfr4`に統一するのが安全。
   **q14（パターンC）だけは実際に動作が変わる**: `EI_v2.yaml`のFreeRADIUS側の実値が`CC!E!nfr4`である以上、
   SW211を問題文どおり`CCIE!nfr4`で設定すると実機でRADIUS認証が失敗する。`CC!E!nfr4`を使うこと。
2. **q14のユーザー名の不一致**: 問題文は「ユーザー名: `ccieuser`」と書いているが、FreeRADIUSの`users`ファイルに実在するアカウントは
   `iseuser`のみ（`ccieuser`というアカウントはRADIUS DBに存在しない）。公式の検証コマンドも`Ssh -l iseuser 10.2.255.211`を使っている。
   実機でSSH+RADIUS認証を試す際のログイン名は`ccieuser`ではなく`iseuser`にする必要がある。
