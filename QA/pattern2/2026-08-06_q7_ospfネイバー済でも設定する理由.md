# Task 1.7 事前設定で OSPF ネイバーが既にあるのに Gi0/0-2 と Lo0 に設定する理由（FULL/DR が要件違反の証拠／R5 は OSPF 皆無）

## 質問

```
R1#sh ip ospf nei

Neighbor ID     Pri   State           Dead Time   Address         Interface
100.255.254.3     1   FULL/DR         00:00:31    100.0.13.2      GigabitEthernet0/1
100.255.254.2     1   FULL/DR         00:00:38    100.0.12.2      GigabitEthernet0/0
R1#
```

事前設定ですでに ospf ネイバーができているのになぜ
Questions/pattern2/pattern2_q7.md

```
int gi0/0-2
ip ospf area 0
ip ospf net point-to-p
mpls ip

int lo0
ip ospf area 0
```

の設定をしている？

## 回答

### 結論

| 打つコマンド | R1 での意味 | 本当の理由 |
|---|---|---|
| `ip ospf 1 area 0`（Gi0/0-2） | **冪等（既に入っている）** | 対向の R5 が OSPF 皆無 → Gi0/2 のネイバーが立っていない |
| `ip ospf network point-to-point` | **必須。未実施** | `FULL/DR` = broadcast タイプ → **Type 2 LSA が生成されている**（要件違反） |
| `ip ospf 1 area 0`（Lo0） | **冪等（既に入っている）** | R3/R5 で欠落。LDP router-id・iBGP の到達性が Lo0 依存 |

質問の show 出力そのものが「設定が足りない」証拠になっている。

---

### 1. ネイバーが「2つしかない」ことに気づけるか

R1 の I/F は Gi0/0・Gi0/1・**Gi0/2** の3本すべてがコア内リンク（`EI_v2.yaml` links 4651/4658/4686）。

```
Gi0/0 ↔ R2   → 100.0.12.2   ✅ 出ている
Gi0/1 ↔ R3   → 100.0.13.2   ✅ 出ている
Gi0/2 ↔ R5   → 100.0.15.2   ❌ 出ていない  ← ここ
```

R1 側の Gi0/2 には初期コンフィグで `ip ospf 1 area 0` が入っている。それでもネイバーが立たないのは、
**R5 の初期コンフィグに `router ospf 1` すら存在しない**から。

```
# R5 初期コンフィグ（EI_v2.yaml）
interface Loopback0
 ip address 100.255.254.5 255.255.255.255      ← ip ospf なし
interface GigabitEthernet8
 ip address 100.0.15.2 255.255.255.252         ← ip ospf なし
router bgp 10000                                ← BGP はある。OSPF プロセスが無い
```

要件「Global SP #1 内の**すべての**内部向けリンクでネイバー関係が確立されていること」は、この時点で未達。

#### Global SP #1（R1〜R6）の初期 OSPF 状態一覧

| 機器 | `router ospf 1` | Lo0 | コア I/F | 本タスクで不足している分 |
|---|---|---|---|---|
| R1 | ✅ | ✅ | Gi0/0 ✅ Gi0/1 ✅ Gi0/2 ✅ | **P2P のみ** |
| R2 | ✅ | ✅ | Gi0/0 ✅ Gi0/1 ✅ Gi0/2 ✅ | **P2P のみ** |
| R3 | ✅ | ❌ | Gi8 ✅ | **Lo0 + P2P** |
| R4 | ✅ | ✅ (mask /31) | Gi8 ✅ | **P2P のみ** |
| R5 | ❌ | ❌ | Gi8 ❌ | **全部** |
| R6 | ✅ | ✅ | Gi8 ✅ | **P2P のみ** |

解答が R1 で `interface range Gi0/0-2` と書いているのは、**6台に同じ手順を流すためのテンプレート**。
R1 単体では no-op だが R5 では必須。打っても害はなく、「確認しなさい」という要件への裏取りにもなる。

---

### 2. `ip ospf network point-to-point` ← これが本命

出力の `FULL/DR` が問題。DR/BDR が選出されている = **ネットワークタイプが broadcast** で、
DR が **Type 2（Network）LSA を生成している**状態。

問題文の要件:

> Global SP #1 内のどのルータの LSDB にも、**Type 2 LSA が存在してはならない**。

つまり **今の `FULL/DR` は、ネイバーが張れている状態であると同時に、要件違反の状態でもある**。
「ネイバーができている」ことと「要件を満たす LSDB になっている」ことは別物。

P2P に変えると DR/BDR 選出そのものが消え、状態は `FULL/  -` になり Type 2 LSA が LSDB から消滅する。

```
R1#sh ip ospf nei
Neighbor ID     Pri   State           Dead Time   Address       Interface
100.255.254.3     0   FULL/  -        00:00:31    100.0.13.2    GigabitEthernet0/1
                  ↑                      ↑
              Pri が 0 に           DR/BDR なし = Type 2 LSA なし
```

**注意点**: ネットワークタイプは Hello に含まれないため、片側だけ P2P にしても隣接自体は上がる。
しかし broadcast 側は自分を DR に選出して Network LSA を出し続けるため **Type 2 は消えない**。
R1〜R6 の全コア I/F に漏れなく打つ必要がある。

---

### 3. `int lo0 / ip ospf 1 area 0`

R1 は既設だが **R3 と R5 は Lo0 が OSPF に入っていない**。これも同じ手順テンプレートの一部で、R1 では冪等。
Lo0 の広告が必須な理由は3つ:

1. **LDP router-id**: 要件「すべてのルータで Loopback0 を LDP ルータ ID として使用」。
   LDP セッションは相手の LDP-ID（= Lo0）宛 TCP 646 で張るので、Lo0 が IGP で到達できないとセッションが成立しない。
2. **iBGP**: R3〜R6 の BGP は `neighbor 100.255.254.x update-source Loopback0`。
   Lo0 到達性がないと VPNv4 セッションごと落ちる（Task 1.8 に直結）。
3. **prefix-suppression との組み合わせ**: 同じ解答で `prefix-suppression` を入れるとコア間 /30 が LSA から消える。
   すると **残る到達手段が Lo0 /32 だけ**になる。Lo0 を広告しなければ全滅。

> 補足: R4 の Lo0 は初期コンフィグで `100.255.254.4 255.255.255.254`（/31）になっている。
> /32 前提の LDP router-id・BGP update-source と噛み合わないので、実機で LDP が上がらなければここを疑う。

---

### 4. `mpls ip`

OSPF ネイバーとラベル配布は別レイヤ。ただし解答には `router ospf 1` 配下に `mpls ldp autoconfig area 0` があるため、
**area 0 の I/F は自動で LDP 有効化される**。各 I/F の `mpls ip` は打ち忘れ防止の保険で、厳密には冗長。

---

### 実機での確認手順

```
show ip ospf interface brief     ← Type 列が BCST なら未達、P2P なら OK
show ip ospf neighbor            ← FULL/DR が残っていないか（全て FULL/ - が正）
show ip ospf database network    ← 「Type 2 LSA が無い」の直接証明。空になること
show ip ospf database router     ← transit link の /30 が消えていること（prefix-suppression）
show ip protocols                ← R5 で「OSPF プロセスが無い」ことの確認
```

`show ip ospf interface brief` は Task 1.5 の QA でも触れた通り **認証やネットワークタイプの詳細は出ない**が、
今回は Type 列があるので P2P 判定には使える。

---

### 一般化できる教訓

「事前設定でネイバーが上がっている」は「要件を満たしている」ではない。
事前設定が満たすのは要件のうち **隣接確立の一部だけ**で、以下は別途設定が要る:

- ネットワークタイプ（Type 2 LSA の有無を決める）
- prefix-suppression（トランジット情報の有無を決める）
- 認証（brief には出ない）
- 対向機器側の設定（`show ip ospf nei` の**行数**を数えて欠落を検出する）
